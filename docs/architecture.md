# 系统架构与设计决策

## 1. 数据流

整个系统围绕一个原则:**用户只产生非结构化输入,所有结构化工作由 AI 完成**。

```
① 输入层   用户随手发消息:"凌晨2点睡,10点起。早:2蛋1奶。练了背40分钟"
              │
② 解析层   AI 解析 → 睡眠8h / 早餐蛋白~14g / 力量训练40min(背)
              │
③ 存储层   写入 Markdown 日志 logs/YYYY-MM-DD.md
          + 更新 profile.md(身体数据变化时)
              │
④ 计算层   每日热量账:摄入 vs 消耗(休息日2400-2500 / 训练日2700-2900 kcal)
          + 当日评价:保肌减脂日 / 掉肌肉风险日 / 热量超标日
              │
⑤ 输出层   每日00:30 定时任务跑 tools/md2docx.js → Word 副本
          + 周日周报:体重趋势 / 缺口均值 / 力量维持情况
              │
⑥ 推送层   docx + 摘要经企业微信通道送达用户手机(规划中)
```

## 2. 记忆机制

AI 跨会话记忆 = 本地文件系统:

- **项目档案**(每计划一个文件夹):计划、日志、进度全在 Markdown 里,任何会话开场先读档案即可无缝续接
- **记忆索引**(MEMORY.md):每个对话开始时加载,记录"哪个计划在哪、进行到哪、有什么约定"
- 效果:换设备、隔一个月、甚至换一个 AI 会话,报出档案位置即可恢复全部上下文

## 3. 关键设计决策

### 3.1 Markdown 是唯一数据源
Word 文档(PPT 同理)是 `tools/md2docx.js` 每日定时从 Markdown 生成的"排版视图"。用户看 Word,AI 写 Markdown,两边永不冲突——因为只有一个源头。

### 3.2 结构化由 AI 做,不由用户做
传统打卡 App 让用户填表单,流失率极高。这里用户发一段口语,解析、分类、估算、写库全部 AI 代办。**表单的填写成本就是坚持的成本,砍掉它**。

### 3.3 评价规则显式化
以减脂期为例,评价规则写死在 plan.md 里,不靠 AI 每次现场发挥:

- 摄入 ≥ 目标蛋白 且 缺口 600-1000 kcal → 保肌减脂日
- 缺口 > 1200 或蛋白 < 100 g → 掉肌肉风险日
- 出现盈余 → 热量超标日

这保证 300 天后的评价和今天口径一致,趋势才可比。

### 3.4 隐私边界
代码、模板、架构公开;真实日志、照片、身体数据永不入仓。`.gitignore` 是隐私边界的代码化。

## 4. 技术栈

- 数据:Markdown + 表格(人可读,AI 可写,Git 可管)
- 转换:Node.js + docx-js(楷体 15pt,标题分级,橙色主题,表格表头底纹)
- 定时:cron 任务(每日 00:30 全量重新生成 Word)
- 解析与报告:LLM(模型无关——系统不绑定任何一家 AI,只依赖"能读写文件"这一个能力)
